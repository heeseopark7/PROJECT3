# shr_loop

**하는 일**: 오른쪽 논리 시프트 코어, "한 비트씩 미는" 버전. `shr_barrel`과 포트가 같다(`i_din, i_shamt, i_fill, o_dout`). 채움 비트를 밖에서 받아서 SRL(0 채움)과 SRA(부호 채움)에 같이 쓴다.

**구조**: 1비트 시프트 단(stage)이 XLEN−1개 직렬로 이어진다. 단 k는 `i_shamt > k`이면 1비트 밀고, 아니면 그대로 통과한다. 그래서 s비트를 밀려면 단 s개가 동작한다. 각 단은 "상수와의 비교기 + 비트마다 2:1 mux"로 이뤄진다. `shamt`는 최대 XLEN−1이라 XLEN번째 단은 절대 동작하지 않아서 만들지 않았다(설계 노트의 "XLEN개"를 이렇게 해석).

**왜 이렇게**
- barrel(`log2(XLEN)`단)과 정반대 극단인 구조라서 구조 비교의 대비가 분명하다. 단 수가 많아 경로가 길어질 것이다.
- 가변 시프트 연산자(`>>` 등)를 쓰지 않고 mux를 직접 그렸다.
- **단을 패킹 벡터 하나의 조각으로 둔다**(`shr_barrel`과 같은 방식, 계층 참조 없음). 상용 합성 툴 호환성을 위한 선택이다. 이 방식은 iverilog에서 단 31개를 시뮬하면 매우 느려서(2000벡터에 92초) 대량 시뮬은 Verilator로 한다(회귀 스크립트 참고). 합성 쪽은 Yosys가 합성한 netlist를 20만 랜덤 벡터로 시뮬해서 `<<` `>>` `>>>` 기준값과 불일치 0임을 확인했다.

**합성 가설** (수치 단정 아님): 면적은 단 수 × 비트 수만큼의 mux라 barrel보다 클 것이고, 지연은 최대 XLEN−1단을 지나므로 barrel보다 훨씬 길 것이다. 기준선을 barrel로 둔 이유(loop가 항상 critical path가 되어 덧셈기 차이를 가림)를 합성에서 확인할 수 있다. 다만 합성 툴이 이 직렬 구조를 그대로 두는지는 볼 점이다.

**검증**: `tb_shifter.v`를 barrel과 같이 쓴다(XLEN 8/16/32, 3연산 × 전체 shamt). `alu_core`, `alu_top` 테스트에서도 `SHIFTER_ARCH` 0, 1의 출력 해시가 같다.
