# adder_cla (Carry-Lookahead 덧셈기)

**하는 일**: RCA처럼 올림이 줄줄이 넘어가지 않고, "이 구간이 올림을 만드는가/넘기는가"를 미리 계산해서 올림을 병렬로 구하는 덧셈기. 속도와 면적이 RCA와 병렬 prefix(KS, BK)의 중간쯤이다. 포트는 모든 덧셈기와 같다.

**먼저 용어**
- **G(generate), P(propagate)**: 구간 전체가 스스로 올림을 만드는가(G), 들어온 올림을 그대로 넘기는가(P). 비트 하나는 `G = a&b`, `P = a^b`.
- **lookahead(미리 보기)**: 구간 4개의 (G, P)를 한꺼번에 합쳐 `G = g3 | p3·g2 | p3·p2·g1 | p3·p2·p1·g0` 처럼 AND-OR 한 층으로 계산하는 것. 올림이 3칸을 거쳐 오는 것을 기다리지 않는다.

**구조** (O3 결정: radix-4 트리)
1. **위로(upward)**: 레벨 0은 비트 하나가 노드 하나. 레벨 1은 4비트 블록, 레벨 2는 16비트 그룹, ... 이렇게 노드 4개를 한 노드로 묶어 (G, P)를 계산해서 뿌리 하나가 남을 때까지 올라간다. 마지막 묶음은 1~3개일 수 있다. W=32이면 비트 32 → 블록 8 → 그룹 2 → 뿌리 1.
2. **아래로(downward)**: 뿌리에 들어가는 올림은 `i_cin`. 그룹 안에서 자식 i가 받는 올림은 `g(i-1) | p(i-1)·g(i-2) | ... | p(i-1)···p(0)·(그룹의 올림)`이다. 이렇게 레벨 0까지 내려오면 모든 비트의 올림이 나온다.
3. **합과 carry-out**: `sum_i = p_i ^ c_i`, `o_cout = G_뿌리 | (P_뿌리 & i_cin)`.
- 모든 노드는 패킹 벡터(G, P, C 각각) 안의 한 비트이고, 인덱스는 "레벨 시작 위치 + 노드 번호"다. 트리 모양(레벨별 노드 수)은 상수 함수로 elaboration 때 계산하므로 W는 4의 배수가 아니어도 된다.

**왜 이렇게**
- 설계 노트의 "4비트 블록 + radix-4 트리"를 그대로 따랐다. 4비트 단위는 AND-OR 팬인(입력 수)이 최대 5라서 한 층으로 만들기에 현실적인 크기다.
- `+`를 쓰지 않았다. lookahead 논리는 AND/OR뿐이다.

**합성 단계에서 볼 가설** (수치 단정 아님)
- 경로 깊이는 레벨 수에 비례(약 `2·log4(W)` 층의 AND-OR)해서 RCA보다 훨씬 짧고, KS보다는 깊이가 비슷하거나 약간 길 수 있다. 대신 셀 수와 배선은 KS보다 적을 것 같다.
- 합성 툴이 AND-OR 큰 팬인을 자기 라이브러리 셀로 재구성하는지가 볼 점이다.

**검증**: `tb_adder_top.v`(W=8 전수, W=16/24/32/40 carry 체인·랜덤, W=32는 100만 벡터)와 `alu_core`/`alu_top`/`mac_top`에서 BEH와 출력 해시가 같아야 한다. lint는 W=8~64에서 경고 0.
