# mac_top (MAC_STAGES = 1, 2, 3)

**하는 일**: MAC(Multiply-Accumulate, 곱해서 누적하는 회로). 매 클록마다 명령 `(i_a, i_b, i_en, i_clr)`를 받아 누산기 `acc`를 갱신한다.
- `i_clr=1`: `acc ← 0` (곱은 무시. `i_en`보다 우선)
- `i_clr=0, i_en=1`: `acc ← acc + a×b` (포화 없이 2^ACC_W로 wrap)
- 둘 다 0: `acc` 유지

**구조** (블록 하나씩) — 앞부분은 `MAC_STAGES`에 따라 다르고, 누산부는 모든 단계에서 똑같다.

| MAC_STAGES | 앞부분 (입력 레지스터 → 누산부로 가는 곱 `p`) | 단 사이 레지스터 | 지연 |
|---|---|---|---|
| 1 | `a_q, b_q` → `mul_top` | 없음 | 2에지 |
| 2 | `a_q, b_q` → `mul_top` → **`p_q`** | `p_q`(2·A_W) + en/clr 2 | 3에지 |
| 3 | `a_q, b_q` → `mul_csa_top`(부분곱 생성·압축) → **`s_q, c_q`** → `adder_top`(최종 합산) → **`p_q`** | `s_q, c_q`(각 2·A_W) + 제어 2, `p_q`(2·A_W) + 제어 2 | 4에지 |

누산부(공통): `p`를 ACC_W비트로 부호 확장한 값을 `adder_top`으로 `acc_q`에 더하고, `clr`(→0) → `en`(→합) → 그 외(유지) 순서로 고른 다음 값을 `acc_q`에 저장한다. `o_acc`는 `acc_q` 그대로다.

- 제어 신호(`en`, `clr`)는 데이터와 **같은 단수만큼** 레지스터를 지난다. 그래야 어느 단계에서나 같은 명령이 같은 순서로 반영된다.
- 레지스터 비트 수(A_W=16, ACC_W=40)는 설계 노트 표와 같다: 1단 74, 2단 108(34+34+40), 3단 174(34+66+34+40).

**왜 이렇게**
- **누산 루프(`acc_q → 덧셈기 → acc_q`)는 1사이클, 안에 레지스터를 넣지 않는다.** 루프 안에 레지스터를 넣으면 한 클록마다 한 번 더하던 것이 두 클록에 한 번이 되어 결과 자체가 달라진다. 그래서 파이프라인 단 수(`MAC_STAGES`)는 곱셈 쪽에서만 나눈다(2, 3단은 3단계 작업).
- **리셋은 상태 레지스터만**: `acc_q`, `en_q`, `clr_q`. 리셋 직후에는 `en_q = clr_q = 0`이라 `a_q × b_q`가 아직 쓰레기여도 누산에 반영되지 않아 `o_acc`가 항상 정의된다. 그래서 `valid` 포트가 필요 없다.
- **`i_clr` 우선(O6, 승인됨)**: `clr`와 `en`이 동시에 1이면 `acc ← 0`.
- **`ACC_W = 2·A_W + 8`**: 가드 비트 8개. 최악의 곱 (−2^(A_W−1))² = 2^(2A_W−2)를 연속으로 더하면 511번까지는 부호 있는 범위 안이고 512번째에 wrap한다(어느 A_W든 같다).
- **지원하지 않는 조합은 컴파일 에러**로 막았다: `MAC_STAGES`가 1~3이 아니거나, `A_W`가 4/8/16이 아니거나, `MAC_STAGES=3`인데 `MULT_ARCH=0`(BEH)인 경우. 더 작은 파이프라인으로 조용히 대체하지 않는다.
- **3단은 구조형 곱셈기 전용**: `*`(BEH)는 툴이 곱셈 구조를 안에서 고르기 때문에 "부분곱 압축 끝"이라는 경계가 없다. 그 경계에 `s_q, c_q`를 놓기 때문에 Array/Booth에서만 가능하다.
- **누산 루프는 2단, 3단에서도 1사이클**이다. 분할은 곱셈 쪽(`p_q`, `s_q`/`c_q`)에서만 했고 `acc_q → 덧셈기 → acc_q` 안에는 레지스터가 없다. 그래서 단 수를 늘려도 이 경로(Q2)는 줄어들지 않는다.
- `adder_top`의 carry-out은 일부러 쓰지 않는다(wrap이라 필요 없음). Verilator의 UNUSEDSIGNAL 경고를 이 이유로 명시적으로 껐다.

**합성 단계에서 볼 가설** (수치 단정 아님)
- 1단에서는 `a_q/b_q → 곱셈 → 누산 덧셈 → acc_q`(Q1)가 가장 길 가능성이 크고, 곱셈기 구조 차이가 가장 크게 드러날 것이다.
- 2단은 곱셈 경로(Q3)가 짧아지지만 누산 루프(Q2)는 그대로라서, 클록을 더 줄여도 어느 시점부터는 Q2가 하한이 될 것이다.
- 3단은 곱셈을 [압축]과 [최종 합산]으로 또 나누므로(Q4) 더 짧아지지만, 레지스터가 늘어(74 → 108 → 174비트) 면적이 커진다. Q2 하한 때문에 이득이 줄어드는 지점을 찾는 게 3단 비교의 핵심이다.

**검증** (`tb_MAC.v`, M3, M4, M5, M6, M7)
- 모델은 명령을 에지에서 즉시 반영하고, DUT의 `o_acc`는 `MAC_STAGES`에지 전 모델 값과 비교한다.
- A 단계 리셋 없는 랜덤, B 단계 클록 중간 비동기 리셋 포함 랜덤(파이프라인 안의 명령이 버려지는 것까지 반영), C 단계 최악의 곱 511회/512회(wrap 경계), D 단계 리셋 직후 0과 복구.
- A_W 4, 8, 16을 전부 돌렸다(M7). `clr/en` 4가지 조합, 양/음 곱, 누산 중 부호 변화, wrap 발생, 리셋 중간 인가를 도달 확인으로 센다.
- 변이 테스트 8가지(en 우선, 부호 확장 제거, 리셋 제거 2종, clr 지연 우회, b_q 우회, carry-in 오류, 음수 포화) 모두 FAIL로 잡혔다.
- **지연 정렬 비교(M5, M6)**: DUT의 `o_acc`를 `MAC_STAGES`에지 전의 모델 값과 비교한다. 같은 시드의 리셋 없는 구간에서 지연 보정 후의 `o_acc` 해시를 찍는데, `MAC_STAGES` 1, 2, 3과 곱셈기 종류가 달라도 같아야 한다.
- 스모크 테스트(1,500사이클)에서 `(MULT_ARCH, MAC_STAGES)` 7가지가 FAIL 0이고 해시가 모두 같았다. 파이프라인 변이(en/clr 한 단 짧음, `p_q` 우회, `c_q` 미등록, 누산 루프 오류) 6가지가 모두 FAIL로 잡혔다.
- **전체 회귀(`run_regress.sh`)는 돌리지 않았다.** `MAC_STAGES` 2, 3 조합이 추가되어 있다.
